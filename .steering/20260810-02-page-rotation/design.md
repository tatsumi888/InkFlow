# 設計書

## アーキテクチャ概要

既存のレイヤ構成（`docs/architecture.md`）はそのまま。回転は `PageSpec` が持つ**ページ単位の属性**として追加し、画像パイプラインの1工程として差し込む。新しいモジュールは作らない。

```
models.PageSpec.rotate  ─┬─→ renderer.required_dpi(rotated=)   解像度の算出に反映
                         ├─→ composer._compose_page()          クロップ直後に回転
                         ├─→ gui/page_view.PageOverlay         プレビューに表示
                         └─→ cli --rotate / プロジェクトJSON     入出力
```

## 回転をどこに挟むか

`composer._compose_page()` のコマ生成で、**クロップ直後・`finalize_page()` の前**に回転する。

```
ページのラスタ → 本文領域でクロップ → コマをクロップ → ★回転★ → finalize_page
                                                                （リサイズ→階調→パディング→量子化）
```

`finalize_page()` の前に置く理由は、回転後の寸法に対して「端末解像度へ contain リサイズ → 白パディング」を行う必要があるため。あとから回転すると、パディング済みの白帯ごと回ってしまい寸法が合わなくなる。

## コンポーネント設計

### 1. models.py

**責務**: 回転値の保持とバリデーション。

```python
ROTATION_NONE = 0
ROTATION_CW   = 90    # 右90°
ROTATION_CCW  = 270   # 左90°
ROTATIONS = (0, 90, 270)
ROTATION_LABELS = {0: "なし", 90: "右90°", 270: "左90°"}
```

- `PageSpec.rotate: int = 0` を追加。JSONキーは `"rotate"`。
- `PageDefaults.rotate: int = 0` を追加し、`to_page_spec()` で引き継ぐ。
- `ROTATIONS` 以外の値は既定（0）へ落とす。既存プロジェクト（`rotate` キーなし）は 0 になる。
- 角度は**時計回り**で表す。90 = 右90°、270 = 左90°。180 は扱わない（「縦横入替」の目的に対して無意味なため）。

定数を `models.py` に置くのは、`models` が Pillow・PyMuPDF・Qt に依存しない純粋モジュールであり、`imaging` / `composer` / `gui` / `cli` のすべてから参照できるため。逆向き（models が imaging を import）にすると純粋性が崩れる。

### 2. imaging.py

**責務**: 実際の回転。

```python
def rotate_image(image: Image.Image, degrees: int) -> Image.Image
```

- `Image.transpose()` を使う。`Image.rotate()` と違い、90°単位では再サンプリングが起きず**画質が劣化しない**うえ速い。
- PIL の `Transpose.ROTATE_90` は**反時計回り**。時計回り90°（右90°）は `ROTATE_270`、反時計回り90°（左90°）は `ROTATE_90` を使う。ここを取り違えやすいので、変換表を定数で持ち、テストで両方向を固定する。
- 0 や未知の値はそのまま返す（呼び出し側で分岐しなくて済むように）。

### 3. renderer.py

**責務**: 回転を織り込んだ必要DPIの算出。

```python
def required_dpi(content_width_in, content_height_in, min_rel, device, rotated=False) -> float
```

- `rotated=True` のとき、端末の幅と高さを入れ替えて計算する。回転後はコマの幅が端末の**高さ**に、高さが**幅**に対応するため。
- 既定引数 `False` にすることで、既存の呼び出しとテストは無変更で動く。

### 4. composer.py

- `_compose_page()` で `spec.rotate` を `required_dpi(rotated=...)` に渡す。
- 俯瞰・各コマとも、`finalize_page()` の直前に `imaging.rotate_image()` を通す。俯瞰も回すのは、1ページ分を読む間に端末を持ち替えずに済ませるため。

### 5. gui/page_view.py

**責務**: 回転が設定されていることをプレビューで示す。

- `PageOverlay.rotation: int` を追加。
- **プレビュー画像そのものは回さない。** 回すと分割枠と読み順番号の位置関係が直感と合わなくなり、「どこで切れるか」の確認という本来の役割を損なうため。
- 代わりに、ページ矩形の左上に角丸のラベルバッジ（例:「右90°」）を描く。円形バッジ（俯瞰の「全」・読み順の数字）とは形を変えて区別する。

### 6. gui/main_window.py

- 右パネルの「このページの分割」に、回転の3択（ラジオボタン横並び）を追加する。`QComboBox` ではなくラジオにするのは、1クリックで選べること、およびフォーカス時のキー入力がレイアウト選択のショートカット（`1`〜`7`）と競合しないため。
- `R` キーで なし → 右90° → 左90° → なし と巡回。
- **既存の `PageSpec` 生成箇所をすべて `dataclasses.replace()` に置き換える。** 現在は `PageSpec(layout_id, include_overview=...)` と組み立てているため、フィールドを増やすと回転設定が落ちる。この取りこぼしが最も起きやすい箇所。
- 記事ツリーのページ行と、プレビュー上部のラベルに回転を表示する。

### 7. cli.py

- `--rotate {none,cw,ccw}` を追加。`_defaults_from_args()` と `_override_project()` の両方で反映する。
- `--rotate` はプロジェクトファイル入力時も全ページへ上書き適用する（`--layout` と同じ挙動）。

## データフロー

### 上下2分割を右90°で出力する
```
1. GUI でレイアウト「上下2分割」を選ぶ（キー 4）
2. 回転「右90°」を選ぶ（キー R）
3. 必要DPI = max(端末高 / コマ幅[inch], 端末幅 / コマ高[inch])  ← 幅高を入れ替えて算出
4. ページを1回レンダリング → 本文領域でクロップ
5. 俯瞰: 本文領域を右90°回転 → finalize_page
6. コマ: 上半分・下半分をそれぞれクロップ → 右90°回転 → finalize_page
7. 出力画像はいずれも 1236×1648
```

## エラーハンドリング戦略

新しい例外は追加しない。不正な回転値は例外にせず既定（0）へ落とす。プロジェクトファイルの前方互換（将来 180 が入っても壊れない）と、既存の `PageSpec.from_dict` の方針（未知のレイアウトIDは既定に落とす）に合わせるため。

## テスト戦略

### ユニットテスト
- `models`: 回転のラウンドトリップ、不正値の既定落ち、`rotate` キーが無い旧プロジェクトの読み込み、出力枚数が変わらないこと。
- `imaging.rotate_image`: 寸法の入れ替わり、右90°と左90°が180°違いであること、0°で同一オブジェクトが返ること、非対称な画像で画素位置が期待どおり移ること。
- `renderer.required_dpi`: `rotated=True` で幅高が入れ替わること、既定引数で既存挙動が変わらないこと。

### 統合テスト
- `composer`: 回転しても出力枚数が変わらないこと、出力寸法が端末解像度ちょうどであること、俯瞰にも適用されること、右と左で結果が異なること。
- **読みやすさの改善そのものを検証する**: `half_v` を回転して出力すると、回転なしより黒画素（＝文字）が多くなる（＝本文が大きく描かれている）。要求の根拠を直接テストで固定する。
- `builder`: 回転を含むプロジェクトのラウンドトリップ。

### GUI テスト
- 回転の選択・`R` キーの巡回・ツリー表示の更新。
- レイアウト変更・俯瞰トグル・「前ページと同じ」で回転が保持／複製されること。
- 保存と読み込みで復元されること。

### CLI テスト
- `--rotate cw` / `--rotate ccw` が反映されること。
- プロジェクトファイル入力への上書き。

## パフォーマンス考慮事項

- `Image.transpose()` は90°単位の画素の並べ替えのみで再サンプリングを伴わないため、劣化もコストもほぼ無い。
- 回転すると必要DPIが変わる（横長のコマでは上がる）。`half_v` の場合、回転なし 240dpi 相当に対して回転時は 320dpi 相当になり、レンダリングは重くなるが1ページ1回の原則は崩れない。

## 将来の拡張性

- 回転の自動提案（コマの縦横比と端末の縦横比を比較して推奨値を出す）を足す場合、`PageSpec` を提案する層として上に差し込める。`composer` から下は変更不要。
- 180° を扱う必要が出た場合、`ROTATIONS` に追加して `imaging` の変換表を1行増やすだけで済む。
