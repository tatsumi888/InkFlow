### 成果

- Python 未導入の環境向けに、コピーだけで使える形になった。

### 計画と実績の差分

**計画と異なった点**:

1. **エントリスクリプトを2本から1本に統合した（設計変更）**
   GUI用とCLI用でエントリを分けると `Analysis` も2つ必要になり、`COLLECT` で同一バイナリが衝突する。第1引数で振り分ける1本にすれば `Analysis` 1つ・`EXE` 2つで済み、解析もライブラリも共有できる。

2. **`InkFlow-cli.exe build` が GUI 起動に化ける不具合を作り込み、実測で発見した（最大の学び）**
   ドラッグ&ドロップされたパスをコマンドと誤認しないよう `Path(argv[1]).exists()` で判定していた。ところがこのリポジトリ自身が PyInstaller の作業用 `build/` を持つため、プロジェクトディレクトリから `InkFlow-cli.exe build ...` を実行すると GUI が起動して応答しなくなった。
   **しかもこの誤った判定をテストで「仕様」として固定していた**（`test_entry_prefers_existing_path_over_command`）。テストが通っていても設計判断が間違っていれば意味がない、という典型例。ドロップされる引数は常に絶対パスなので、パス区切りの有無で判定すれば十分かつカレントに左右されない。

3. **サイズ削減が計画外に必要だった**
   素のビルドは 169.9MB（ZIP 74.5MB）で、月1回の道具としては重い。未使用 Qt DLL・`opengl32sw.dll`・Pillow の AVIF デコーダを spec で除外して 123.9MB（ZIP 54.6MB）にした。ただし「落としすぎ」は起動するまで分からないため、検証手段（下記）が先に必要だった。

4. **`selftest` サブコマンドを追加した（計画外）**
   当初の動作確認は `layouts` の出力を見るだけで、**Qt を一度も初期化していなかった**。これでは Qt DLL の除外が妥当か検証できない。PDF読み込み → 画像処理 → EPUB書き出し → Qt初期化 → アイコン生成まで実際に通す `selftest` を足した。配布先で動くかを利用者自身が確かめる手段にもなる。

5. **凍結実行ファイルの文字コード問題**
   PyInstaller のランタイムは `PYTHONIOENCODING` を無視する。日本語Windowsのコンソールは cp932 なので、em dash を print しただけで `UnicodeEncodeError` で落ちた。CLI 側で `errors=backslashreplace` に再設定し、子プロセスの出力を読む側も cp932 で復号するようにした。

**新たに必要になったタスク**: 上記 3〜5 に加え、`build.py` の `--specpath` が spec 指定時に使えない点の修正。

**技術的理由でスキップしたタスク**: なし。全タスクを完了した。

### 学んだこと

**技術的な学び**:

- **テストが通っていても、テストが固定しているのが誤った仕様なら意味がない。** `test_entry_prefers_existing_path_over_command` は「カレントに同名フォルダがあればコマンドとみなさない」を正しく検証していたが、その仕様自体が誤りだった。テストを書くときは「この振る舞いは本当に望ましいか」を、実装の都合とは別に問う必要がある。
- **パッケージングの検証は「起動してみる」以外にない。** 依存の取りこぼしは静的解析でもテストでも捕まらない。しかも今回は「動作確認」と称して Qt を一度も初期化していなかった。検証を書いたら「それは本当に対象を通っているか」を確認する（この見落としは implementation-validator も指摘した）。
- 凍結環境は通常の Python 実行と前提が違う: `PYTHONIOENCODING` が効かない、`sys.stdout` が `None` になりうる（windowed）、`sys.executable` がアプリ自身を指す。これらは実行してみるまで表面化しない。
- PyInstaller で1つの `Analysis` から複数の `EXE` を作れる。コンソール有無だけが違う実行ファイルを作るのに向いている。
- Qt の DLL は Python モジュールの `excludes` では落ちない。`Analysis.binaries` を名前で絞る必要がある。

**プロセス上の改善点**:

- 「サイズを削る」より先に「削って壊れていないか確かめる手段」を作ったのは順序として正しかった。`selftest` があったので、除外リストを攻めた設定にしても安心して進められた。
- implementation-validator の指摘のうち、GUI経路が検証されていない件と CLI 実行ファイルの引数なし起動は、自分では気づけていなかった。実装者と検証者の視点は実際に違う。

### 次回への改善提案

- **「その検証は本当に対象を通っているか」を検証タスクの受け入れ条件に含める。** 今回「GUI実行ファイルの動作確認」を完了扱いにしていたが、中身は CLI ロジックを別サブシステムで走らせただけだった。
- 環境依存の不具合（カレントディレクトリ・文字コード・凍結の有無）は、**実運用に近い場所から実行して**初めて出る。今回はたまたまプロジェクトディレクトリから実行して発見できたが、意図した検証ではなかった。検証時の作業ディレクトリを意識的に変えて試す。
- テストが「実装の都合」を固定していないか、レビュー時に一度疑う。
