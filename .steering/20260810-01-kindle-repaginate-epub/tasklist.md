### 必須ルール
- **全てのタスクを`[x]`にすること**
- 「時間の都合により別タスクとして実施予定」は禁止
- 「実装が複雑すぎるため後回し」は禁止
- 未完了タスク（`[ ]`）を残したまま作業を終了しない

### 実装可能なタスクのみを計画
- 計画段階で「実装可能なタスク」のみをリストアップ
- 「将来やるかもしれないタスク」は含めない
- 「検討中のタスク」は含めない

### タスクスキップが許可される唯一のケース
以下の技術的理由に該当する場合のみスキップ可能:
- 実装方針の変更により、機能自体が不要になった
- アーキテクチャ変更により、別の実装方法に置き換わった
- 依存関係の変更により、タスクが実行不可能になった

スキップ時は必ず理由を明記:
```markdown
- [x] ~~タスク名~~（実装方針変更により不要: 具体的な技術的理由）
```

### タスクが大きすぎる場合
- タスクを小さなサブタスクに分割
- 分割したサブタスクをこのファイルに追加
- サブタスクを1つずつ完了させる

## 実装後の振り返り

### 実装完了日
2026-08-10

### 成果

- テスト 253件すべてグリーン。
- 実運用規模（B5・原稿40ページ・Paperwhite 1236×1648）で検証:
  - 出力 201ページ（表紙込み）、しおり5件、**32.2MB**、生成時間**44秒**（原稿1ページあたり1.11秒）
  - 目標だった「50MB以下」「パンなしで読めるサイズ」を達成
- 受け入れ条件はすべて自動テストで担保。CLI と GUI の出力一致もテストで固定した。

### 計画と実績の差分

**計画と異なった点**:

1. **オーバーラップを軸ごとに制御するよう変更した（設計変更）**
   計画では「矩形を四方に膨らませる」としていたが、実際に出力画像を目視したところ、2段組4分割の左上コマの右端に**隣の段の文字が混入**していた。段間（ノド）方向のオーバーラップは読みやすさに寄与せず、画面を無駄にするだけだと分かった。`Layout.overlap_axes` を追加し、「行を断つ向き」にだけ効かせるようにした。設計だけでは気づけず、成果物を見て初めて判明した種類の問題。

2. **サイズ削減の手段が想定と逆だった（案内文の訂正）**
   計画では「サイズが大きいときは JPEG に切り替える」と案内するつもりだったが、実測では JPEG が PNG の**3倍以上**（32MB → 106MB）に膨らんだ。文字の輪郭が多い誌面では JPEG が不利で、効くのは階調数を下げること（16→4 で 33MB → 17MB）だった。副次的に、シャープをかけると**サイズが減る**（42MB → 33MB）ことも分かった。画素が両極に寄って圧縮が効くため。

3. **画像処理の順序を設計から入れ替えた**
   白パディングを階調調整の前に置く設計だったが、白い余白がヒストグラムを歪めて自動コントラストを鈍らせるため、`リサイズ → 階調調整 → パディング → 量子化` の順にした。

4. **設定ダイアログを別ファイルに分離した**
   `main_window.py` が肥大化したため `gui/settings_dialog.py` を切り出した。

**新たに必要になったタスク**:

- CLI に `layouts` / `devices` サブコマンド — 設定値（レイアウトID・端末ID）を調べる手段がないと、CLI 単体で使えなかったため。
- CLI に `--gray-levels` — サイズ削減の主要手段だと実測で分かったので、CLI からも触れる必要があった。
- 階調数の選択肢に 4・8 を追加 — 同上。当初は 16/32/64/256 だった。
- プレビューへの余白トリム位置の表示（緑の破線）— 自動トリムが意図どおりか確認する手段が必要だった。
- PDF のドラッグ＆ドロップ追加 — 姉妹プロジェクト Clipper と操作感を揃えるため。
- ワーカーの中断対応と書きかけEPUBの削除 — 200ページの生成は中断したくなる長さがあった。

**技術的理由でスキップしたタスク**: なし。全タスクを完了した。

### 学んだこと

**技術的な学び**:

- **成果物を目視するまで分からない欠陥がある。** オーバーラップの軸の問題は、テストも設計レビューも通り抜けた。分割位置の計算は正しく、テストも「オーバーラップで矩形が広がる」ことを正しく検証していた。にもかかわらず読書体験としては明確に劣化していた。画像を出力する機能では、パイプラインの検証に**実際の出力画像を見る工程**を組み込む必要がある。
- **サイズや速度は測るまで直感が当てにならない。** JPEG が有利という思い込み、シャープでサイズが増えるという思い込みが、どちらも実測で覆った。UIの案内文のような「ユーザーに行動を促す文言」は、必ず実測に基づかせる。
- Pillow は、パレットが16色以下の `P` 画像を PNG に保存すると自動的に4bit深度で書く。16階調グレーの誌面画像はこれで大幅に縮む。
- レンダリング解像度を「余白トリック後のサイズ」から決めるには、先に安価な下見レンダリング（72dpi）が要る。この二段構えが画質とコストの両立点だった。
- Qt のショートカットはウィジェットのキー入力より優先されるため、数字キーをショートカットに使うならメインウィンドウにテキスト入力を置けない。テキスト入力をモーダルダイアログ側に寄せる設計で回避した。

**プロセス上の改善点**:

- レイヤを下から積む順序（純粋ロジック → 画像 → 出力 → UI）が有効だった。各層でテストを通してから上に進めたので、GUI の実装時にはコアの挙動を疑わずに済んだ。
- 純粋モジュール（`layouts` / `models` / `devices`）を外部ライブラリから切り離したことで、レイアウト仕様のテストが軽量かつ高速になり、オーバーラップの仕様変更にも数分で追随できた。
- 統合テストに小さな端末プロファイル（`custom:150x200`）を使ったことで、253件のテストが実用的な時間で回った。

### 次回への改善提案

- 画像を生成する機能では、**タスクリストに「出力画像を実際に見る」タスクを明示的に入れる**。今回はフェーズ7で偶然目視して不具合を見つけたが、計画段階では「目視確認」を成果物の寸法とサイズの確認としか書いていなかった。
- 「ユーザーに提示する数値・推奨」を含む機能は、実装タスクとは別に**計測タスク**を立てる。今回は案内文を書いた後に実測して書き直す手戻りが発生した。
- 実物に近い入力（B5・2段組・40ページ）での検証を、フェーズ7ではなく**画像パイプライン完成直後**に一度挟むと、オーバーラップの問題をより早く発見できた。
