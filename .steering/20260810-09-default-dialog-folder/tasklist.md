### 計画と異なった点

**予期していなかった技術的発見**: 新しいテスト（`export_epub()` を通して実際に `BuildWorker` を起動するテスト）が、フルスイート実行時にのみ `Windows fatal exception: code 0xc0000374`（ヒープ破損）でプロセスごとクラッシュする問題を引き起こした。原因は、ワーカーの `succeeded`/`finished` シグナルがキュー投函されたまま処理されず、テスト対象の `window` が破棄された後も残り続け、**後続の無関係な別テストが `qapp.processEvents()` を呼んだ瞬間に配送されて**クラッシュしていたこと。既存の `test_build_worker_produces_epub` が `worker.wait()` の直後に `qapp.processEvents()` を呼んでいたのは、まさにこの問題への対処だったと分かった（既存コードを見ていた時点では理由が明記されておらず、意図に気づいていなかった）。
今回のテストでは、確認したいのが「フォルダを覚えたか」という同期的な副作用だけだったため、`BuildWorker.start` を no-op にしてスレッド自体を起動しない設計に変更し、根本的にこの種のクラッシュを起こしようがない形にした。

### 学んだこと

**技術的な学び**:
- QThreadベースの非同期処理をテストするとき、「スレッドの終了を待つ」（`wait()`）ことと「シグナル配送を完了させる」（`processEvents()`）ことは別の作業であり、後者を怠るとテスト自体は成功して見えても、**キューに残ったイベントが後続の無関係なテストを巻き込んでクラッシュさせる**ことがある。これはテストの独立性を破る重大な副作用であり、かつ「自分のテストは green なのに別のテストが原因不明で落ちる」という診断しにくい形で現れる。
- 非同期処理の副作用を検証するテストでは、「本当に非同期実行が必要か」を先に問う。今回のように同期的な副作用（`_remember_dialog_dir` の呼び出し）だけを見たいなら、スレッド自体を起動しない（no-op化する）方が、検証したいものに対してテストを最小化でき、かつクラッシュのリスクも無くなる。

**プロセス上の改善点**:
- フルスイート実行で初めて顕在化する問題（個別テストや部分実行では再現しない）があることを踏まえ、新しいGUIテストを書いたら**必ずフルスイートで確認する**運用を今後も徹底する。今回は絞り込み実行（`-k`）でグリーンを確認した後、フルスイートで初めてクラッシュに気づいた。

### 次回への改善提案
- `BuildWorker` や同種の `QThread` を扱うテストを新たに書くときは、今回の教訓（`wait()` 後に `processEvents()` を呼ぶか、そもそも `start()` をno-op化するか）をテンプレートとして最初から適用する。
