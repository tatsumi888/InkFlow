### 成果

- `.github/workflows/build.yml` を追加。`v*` タグ push で GitHub Release に配布物を添付、`workflow_dispatch` でアーティファクトのみ取得できる。

- タグとパッケージバージョンの整合確認、`pytest` ゲートを内蔵。

### 計画と実績の差分

**計画と異なった点**: なし。設計どおりに実装した。

**スキップしたタスク**:
- 実際にタグを push してワークフローの実行結果を確認するステップ。タグ push はリリースを意味する操作（GitHub Release の作成、公開）であり、ユーザーに無断で実施すべきではないと判断した。YAML構文の妥当性と埋め込みロジックの検証はローカルで完了しており、実行そのものはユーザーがタグを打つタイミングで初めて意味を持つ。

### 学んだこと

**技術的な学び**:
- GitHub Actions の `on:` キーは、汎用YAMLパーサ（PyYAML の既定リゾルバなど、YAML 1.1 準拠）だと bareword `on` がブール `true` と解釈されることがある（有名な落とし穴）。GitHub Actions 自体は専用のワークフロー構文パーサを使うため実害はないが、ローカルでYAMLの中身を検証するスクリプトを書くときはこの点に注意する。
- `packaging/build.py` を「開発用スクリプト」として作っておいたことが、CI連携でそのまま効いた。CI固有のビルドロジックを新たに書く必要が一切なく、ワークフローは薄いオーケストレーションに徹せられた。パッケージング機能を作った時点でのこの設計判断（`.steering/20260810-03-standalone-packaging/design.md` 参照）が、今回の作業を軽くした。

**プロセス上の改善点**:
- 「タグを打って実際に動かす」という、ユーザーの判断を要する操作の手前で作業を止めたのは妥当だった。ローカルで検証できる範囲（YAML構文・埋め込みロジック）はやり切ってから止めている。
