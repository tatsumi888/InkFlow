# プロダクト要求定義書（PRD）

## 1. 背景と課題

雑誌（B5〜A4）の記事PDFを Kindle Paperwhite で読もうとすると、次のジレンマに突き当たる。

| 読み方 | 問題 |
|---|---|
| ページ全体表示 | B5〜A4の版面が6インチ級の画面に収まるため、本文が小さすぎて読めない |
| 拡大表示 | 読めるサイズにすると1画面に収まらず、パン（スクロール）が必要。電子ペーパーは再描画が遅くタッチ追従も悪いため、パン主体の操作は実用に耐えない |

一方、PDFをEPUBへ変換する既存の手立ても、雑誌には向かない。

- **テキスト抽出＋リフロー**: 多段組・図版・キャプションが混在する誌面ではレイアウトが崩壊する。
- **1ページ＝1画像のEPUB**: レイアウトは保持されるが、結局「ページ全体表示」と同じで文字が小さい。

## 2. プロダクトの狙い

**拡大とパンを、あらかじめ「ページ送り」に変換しておく。**

版面を読み順に切り分け、各コマを端末の画面いっぱいに割り付けた固定レイアウトEPUBを事前生成する。読者は端末上でページを送るだけで読み進められ、拡大もパンも不要になる。

ページを画像として扱うため、レイアウトは100%保持される。

## 3. 対象ユーザーと利用シーン

- 単独の個人ユーザー（本プロジェクトの依頼者）。Windows 11 / Kindle Paperwhite を所有。
- 月刊誌を購読しており、**記事ごとに分冊されたPDF**を手元に持っている。
- 同期は**月1回**。1号あたり全体で**40ページ程度**。
- 完全ローカル処理。外部サービスへの送信は行わない。

## 4. 提供する価値（成功指標）

| 指標 | 目標 | 実測（B5・40ページ） |
|---|---|---|
| 本文の可読性 | パンなしで読めるサイズ（既定4分割時、本文文字高が画面高の1/40以上） | 達成（1236×1648に4分割コマを割り付け） |
| 1号あたりのファイルサイズ | 50MB以下（Send to Kindle のメール添付上限） | 32MB（16階調）/ 17MB（4階調） |
| 編集にかかる操作 | 既定のまま送るなら操作ゼロ、例外ページのみ手当てして5分以内 | 達成（既定レイアウトが全ページに自動適用） |
| 生成時間 | 実用範囲 | 45秒（原稿1ページあたり1.1秒） |
| 同期回数 | 月1回・1ファイル | 全記事を1冊にまとめ、記事ごとのしおりで移動 |

## 5. 機能要求

### 5.1 再ページ化（必須）

- 原稿1ページを、選択したレイアウトに従って複数コマへ切り分ける。
- 既定は「ページ全体（俯瞰） → 左上 → 左下 → 右上 → 右下」の**5ページ展開**（二段組4分割）。
- レイアウトは**ページ単位**で選択できる。全体のみ／二段組4分割／一段組4分割／上下2分割／左右2分割／二段組6分割／上中下3分割。
- 分割線上の行が読めなくなるのを防ぐオーバーラップ。行を断つ向きにだけ効かせる。
- 周囲の白余白を自動トリムしてから分割し、本文の実効表示サイズを最大化する。
- **縦横入替（回転）をページ単位で選べる**（なし／右90°／左90°）。横長のコマは回して端末を横向きに持つと画面を使い切れる。回転はそのページの出力すべて（俯瞰を含む）に適用する。

### 5.2 Kindle最適化（必須）

- 出力画像は端末解像度ちょうど（既定 1236×1648）。縦横比は保ち、余りは白で埋める。
- グレースケール化・自動コントラスト・ガンマ補正・アンシャープマスク。
- 16階調に量子化（4bit PNG）。階調数は変更できる。

### 5.3 EPUB出力（必須）

- 1画像＝1ページの固定レイアウトEPUB3。Kindle が固定レイアウトとして解釈するメタデータを付与。
- **記事ごとのしおり**。目次は `nav.xhtml` と `toc.ncx` の両方。
- 表紙は雑誌名＋号から自動生成。任意の画像も指定できる。

### 5.4 GUI（必須）

- 記事PDFの追加（D&D対応）・並べ替え・しおり名の編集。
- プレビュー上に分割枠と**読み順の番号**、余白トリム位置を重ねて表示。
- ページごとのレイアウト選択と、「前ページと同じ」「この記事の全ページに適用」「全ページに適用」。
- キーボードだけで一周できる操作系。
- プロジェクトの保存・再開。

### 5.5 CLI（必須）

- 保存済みプロジェクト、またはPDFを並べたフォルダから、GUIを起動せずEPUBを生成。
- GUI と**同一の出力**であること。

## 6. 非機能要求

- **完全ローカル**。ネットワーク通信を行わない。
- **メモリ**: 200ページ規模の生成でも出力画像を同時に保持しない。
- **再現性**: 同じプロジェクトからは同じページ画像が生成される。
- **堅牢性**: 1記事の失敗時、どの記事のどのページかをメッセージに含める。パスワード保護PDFは明示的に拒否する。

## 7. スコープ外

- テキスト抽出によるリフロー型EPUBの生成
- OCR、本文・段組の自動検出
- 傾き補正・ノイズ除去などのスキャン画像向け前処理
- 縦組み（右→左）専用の読み順プリセット
- MOBI/AZW3 出力、Kindle端末への自動転送
- 見開き（2ページ連結）の扱い

## 8. 意思決定の記録

| 論点 | 決定 | 理由 |
|---|---|---|
| テキスト化 vs 画像 | **画像** | 多段組の雑誌ではリフローでレイアウトが崩壊するリスクが高い。ベクタは失うが確実性を取る |
| EPUB vs PDF | **EPUB（画像固定レイアウト）** | Kindle のライブラリ・目次・読書位置が効く。KindleのPDFビューアは目次もコントラスト調整も弱い |
| 段組の自動検出 vs 人手選択 | **人手選択** | 雑誌のレイアウトは多様で、誤検出のリカバリコストが高い。40ページなら人手でも数分 |
| 分割の粒度 | **既定は4分割＋俯瞰** | 依頼者の想定。俯瞰があると誌面構成を把握してから読める |
| サイズ削減の手段 | **階調数を下げる** | 実測でJPEGは3倍以上に膨らんだ。文字主体の誌面ではPNG＋低階調が正解 |
| 回転の判定 | **ページ単位の人手選択** | 横長のコマでは文字が1.33倍になるが、縦長のコマでは0.75倍に悪化する。誌面依存なので自動化しない |
| 回転の適用範囲 | **俯瞰ページも含めて回す** | 1ページ分を読む間に端末を持ち替えずに済ませるため |
