# 設計書

ドキュメント作成タスクのため、コード設計は無い。方針のみ記す。

## 方針

- 各スキルのテンプレート構成を尊重しつつ、TypeScript/Web向けの記述（レイヤ分割・DB前提の項目など）はPython単一パッケージのデスクトップアプリに合わせて読み替える。該当しない項目（API設計、DB制約など）は簡潔に「該当なし」とするか省略する。
- `functional-design.md` は `architecture.md` と役割を分ける。`architecture.md` が「どう組み立てるか」（レイヤ・依存関係）、`functional-design.md` が「何が起きるか」（画面遷移・データ構造・アルゴリズム・エラー分類）を扱う。
- `repository-structure.md` は実際のディレクトリ構成をそのまま記述する。スキルの汎用テンプレートが提案する「`.steering/` はgitignore対象」という例は、このプロジェクトの実際の方針（`.steering/` はgit管理する）と矛盾するため**採用しない**旨を明記する。
- `glossary.md` はコード上の識別子（`PageSpec.rotate_overview` 等）と日本語のドメイン用語（俯瞰・分割コマ・縦横入替）を対応付け、今後のドキュメントや会話で表記が揺れないようにする。
- 齟齬の発見は「ドキュメントを読み直す」ことで能動的に行う。今回、`CLAUDE.md` の「このディレクトリはGitリポジトリではない」という記述が、実際にはセッション中盤でGit初期化・GitHub pushを済ませたにもかかわらず更新されていなかったことが見つかった。これは典型的な「実装は進んだがドキュメントが追従していない」パターンであり、ドキュメント整備タスクの価値を裏付ける実例として振り返りに残す。

## テスト戦略

ドキュメントに対する自動テストは無い。整合性確認は目視レビュー（記載内容と実際のコード・設定ファイルの突き合わせ）で行う。
